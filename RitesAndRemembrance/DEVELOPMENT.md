# Development notes

## Version 0.9.1 annual ceremony

`event.nextCeremonyAt` is persisted at dance start as `started + serverWorld:getYearLength()`, independently of reward expiry. Preview and gather RPCs reject a retained event until that deadline, with remaining time rounded up to tenths of a game day. Gathering cancellation is free; a started dance consumes the year even if interrupted or unrewarded. Legacy retained events with a `started` timestamp migrate lazily from that timestamp. Older overwritten history cannot be reconstructed. Invalid year lengths block dance start and legacy migration. A configured year change does not resize existing deadlines. The original active-reward guard remains for custom years shorter than the reward. Offline tests cover both local editions, boundary expiry, persistence, migration and cancellation/no-reward paths.

## Version 0.9.0 tribal ceremony

Author: Vittorio. `tribalCeremony.lua` owns the persisted per-tribe preview/gather/dance/completed/cancelled state in the existing mod database. The RPC derives the tribe from its authenticated client, accepts only action/target IDs/serial and bounded selection geometry, and resolves targets, roster, positions, reward and duration on the server. Previews expire after 180 simulation seconds; selected participant IDs and collision checks are revalidated before interruption. A saved active-tribe index drives one update per half simulation second independently of client polling. Action contexts bind both tribe and event serial. Missing/stale saved orders cancel themselves; replacement orders are never cancelled by event cleanup.

Lost invitations are retried at most twice automatically with a 15-second minimum interval and at most eight successful automatic invitations per update. Manual reinvitation uses the same interval but permits further attempts. Valid current orders are preserved to avoid restarting asynchronous paths. Native cancellation releases manual assignments, held items, seats and wait orders before adding a new native path. `allowToFinishEvenWhenVeryTired` prevents ordinary sleep desire from cancelling the ceremony; incapacitation and emergency exclusions remain. This addresses verified code gaps, not proof of a specific live pathfinding failure.

`ceremonySelection.lua` validates finite radius/box bounds (at most 100 metres), rejects unknown fields and filters server-owned standing places. `ceremonySelectionUI.lua` reuses the native popup control, selection icons, radar/box models and mouse conventions. The native multiSelectUI singleton has no custom-data callback and therefore is not repurposed or globally patched. Selection affects the offered ring positions; box selection does not rearrange them into a grid.

`ceremonyRewards.lua` shares exact threshold arithmetic between preview and server: population >=25, attendance >=25%, +2 mood above 50% and +1 otherwise, rounded 20 × attendance fraction work percentage, one day below 50% and three days otherwise. The denominator cannot fall below the population recorded at gathering. Only uninterrupted dancers receive rewards. `rrTribalUnityFull` is the stable internal identifier for the +2 majority effect; its name does not imply 100% attendance. `rrTribalUnity` preserves legacy +1 effects. Saved `rrTribalUnityWorkPercent` controls the individual work multiplier and is cleared when both effects expire; an absent field preserves old 0.8.0 work bonuses at 10%.

`ceremonyFormation.lua` uses the spherical world's tangent plane and distinct slots spaced at least 2.04 metres apart. Rings are 2.4 metres apart and can skip blocked positions. Native surface/raycast and collision-box helpers reject water, steep surfaces and excessive height differences. Standing-space validation is distinct from route validation: native paths are created after summons and may fail. The 300-second limit and explicit partial-start/cancel controls prevent permanent waiting. Counts and geometry are bounded to 512 members and 24 rings. No new models, game objects, GLBs or helper-node assets are generated.

`ceremonyUI.lua` is a non-pausing modal owned by gameUI, with a schematic overhead placement preview. It uses the existing ten-second request scope, serializes mutations, suppresses obsolete poll responses and invalidates callbacks on close/tribe change/reinitialization. Status polling changes only the text while the phase/serial is unchanged. The native addPlans client dispatch is intercepted before any work plan reaches the server. The shared planHelper adapter adds the entry to single-object and single-ground selections only after the remembrance skill's discovery.

The server action sequence is move / gather / dance. Stationary server stages have infinite native completion frequency and are advanced by the saved ceremony controller. The logic VM maps the stationary stages to native idle before the low-level animation override, preserving the previous crash fix. Named dance1..dance4 skeleton poses are resolved read-only from the native setup closure with a bounded, cycle-checked Lua debug-upvalue walk, avoiding hard-coded frame numbers or copied trigger callbacks. If an unfamiliar/stripped setup hides that enum, the animation safely falls back to the supported seated remembrance pose. All four installed humanoid rigs expose the four distinct dance poses in regression tests. Each participant has a stable, small animation-speed variation.

`workBonus.lua` scales only the active productive action's speed argument to native activeOrderAI. It does not change global speed, skill-learning multipliers, travel, research, needs or native effect timers. The existing effect impact/affectsLoyalty system handles mood targets. Native one/three-day timers are calculated once at completion from `serverWorld:getDayLength()`; world time also guards the saved tribe cooldown. Completion is marked before rewards to prevent repeated grants. As with existing memorial receipts, the engine does not expose an atomic transaction across the mod database and all native sapien saves: a process crash during completion can still produce a partial reward. No claim of transactional save atomicity is made.

Validation: `rites-preview/test_runtime.py` checks existing behavior plus the installed native selector and no-object stationary AI stages. `rites-preview/test_tribal_ceremony.py --edition Public|Unstable` uses native Lua/vector libraries for formation and lifecycle tests with controlled physics/path scheduling, and native radial sendPlan/timer code for UI fault injection. Both selected installations currently report executable version 0.7.0.2; this is not a live run of Public 0.6.1.3. Test actual travel on slopes/floors/crowded sites, threats during the dance, native save/reload and multiplayer in-game before release. Large-tribe engine performance is not measured by offline geometry tests.

## Persistence and construction

The per-world ritesRemembrance_v1 database retains schema 1 and stable model keys. It stores one record per deceased Sapien, a paged-by-key FIFO per tribe, and memorial metadata indexed by constructed object ID. A poll advances through at most 32 completed records.

The native build plan consumes catalog resources using normal delivery/construction. A short-lived server context lets the creation adapter attach memorial metadata and save the object-ID mapping. Native construction and deconstruction replace shared state; the object-type-change adapter restores memorial fields afterward. The context is cleared even if creation throws.

Name, age, death time and appearance are server snapshots. Portraits retain the original Sapien ID because native face generation uses it. Only known appearance fields are copied. Older records remain readable without portraits.

Repeated successful placement requests return the saved object ID. Placing an order completes the death's decision even if later cancelled or demolished. Engine creation and database writes are separate operations: an abrupt process failure between them is not atomic and can leave an orphaned order.

## Security and compatibility

Authenticated connections determine tribe ownership. Clients cannot choose names, portraits, ages, tribe IDs, resource counts or arbitrary object state. Actions and fields are allowlisted; transforms must be finite with orthonormal right-handed rotations. Material restrictions permit only valid variants and cannot disable every candidate in a category. Generic native build/clone requests cannot create memorials outside the validated death flow.

Placement uses native client terrain, slope, water and collision checks. The server validates numeric bounds and authorization but does not repeat all geometric checks. Gameplay input cannot execute commands, evaluate code or select filesystem paths.

New memorials delegate deconstruction to the native handler after ownership checks. Legacy resource-free objects use native removal without refunds. Other objects retain their original handlers.

The Family Tree bridge checks enabled world mods and reuses this project's Family Tree UI functions in an independent instance. Closing inspection invalidates pending callbacks and hides its parent-owned container; reopening reuses it. Inspector reload invalidates the cached instance. The living-person panel remains independent. The death hook chains the previous callback so both mods can record the death.

## Version 0.6.0 collective remembrance

`familyVisit.lua` coordinates a server-owned rendezvous per grave. The authenticated client supplies only the grave ID. Ownership, research, completed construction, recorded kinship, active effects and ability to participate are checked server-side. The participant list is deduplicated, sorted and fixed when requested, using loaded living members of the deceased's saved family snapshot in the same tribe. There is no historical or later-born family reconstruction. Normal own-tribe sapiens are loaded by the game; unloaded or emigrated relatives are outside this invitation scope.

The new order uses three native action-sequence stages: move to the grave, wait for the family, and remember together. Waiting and ceremony actions use non-completing native action timers; the saved rendezvous advances everyone through `serverSapien:startNextAction` in one server update and completes through `serverSapien:completeOrder`. Native movement, fatigue and threat handling run before the coordinator. Custom animation routing applies only to stage three, so arriving early does not start a solo ceremony. Client rendering/network delivery can differ slightly in frame timing; no render-frame synchronization is promised.

Saved `familyVisit:<graveID>` records contain a monotonic per-grave serial, participant IDs, phase and simulation timestamps. Order contexts carry this serial and the memorial ID. A cancelled, missing or replaced participant order cancels the remaining matching orders without cancelling replacement work or combat. Gathering times out after 300 simulation seconds. Remembering requires everyone to remain within three metres for eight simulation seconds. Superseded saved orders cannot join later ceremonies. Completed/cancelled records are retained for serial allocation, bounded to one record per grave. Routine work is explicitly allowlisted for native interruption; sleep, combat, medical/delivery work and unknown mod orders are rejected before assigning anyone. Assignment failure rolls back ceremony orders; interrupted routine jobs are subsequently reconsidered by native AI.

`rrFamilyRemembered` is a native +1 effect with `affectsLoyalty=true` and a 2,000-second timer. Both visit types reject recipients with either visit effect already active, across all graves. Completion also updates Happiness and Loyalty immediately, capped at five. The native social API `serverSapien:addToBondAndMood` adds 0.1 to short-term bond and relationship mood in each ordered participant pair; it clamps to 0–1 and saves lazy private state. Native pleasant social interactions use 0.2; the ceremony uses half that increment. Long-term values, family and partner flags are untouched and continue their normal evolution. One survivor receives the mood effect but no relationship mutation.

The event is marked completed before rewards and native order completion to block reentrant or duplicate grants. As with existing construction receipts, game object saves and the mod database are not transactional: a process crash between these writes can lose part of a ceremony's reward. Ordinary save/reload retains the event and effect timers. No client-provided code, paths, recipients, durations or relationship amounts are evaluated.

## Version 0.4.1 preview fixes

build_native_previews.py exports four default meshes and thirteen component alternatives. It computes one union of all resource geometry alternatives per design, centers that union, and scales its radius to 0.60 inside a 0.75 bounding sphere. Camera offsets are zero; the same framing applies to the default mesh and every material combination. This preserves bases and avoids camera jumps on material changes without scaling world objects.

preview.lua resolves each resource group through getAvailableGameObjectTypeIndexesForRestrictedResource, matching native first-allowed ordering. It retrieves the chosen resource model path/material remap and combines prepositioned parts using the native composite-model API. Each group uses separate material aliases registered as native material clones in deterministic order; changing a stone block therefore cannot recolor the small-rock border. Normals, UVs and source geometry are retained. Only generated allowlisted paths are used. An unsupported modded mesh shows an unavailable-preview message instead of a misleading default.

The Use only callback rebuilds the preview composite and its cache key; iconIsUniquePerObject bypasses the native same-object-type early return. Empty material selections hide the preview and keep native placement disabling. UI-only preview state is never written to the world or accepted from server requests.
